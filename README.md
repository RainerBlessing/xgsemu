# XGS Emulator

XGS Emulator is an emulator for the XGameStation Micro Edition (XGS ME): an
Ubicom/Parallax SX52 microcontroller running at 80 MHz, with video generated by
the program itself, SRAM, a joystick port and a ROHM BU8763 sound chip. It runs
the compiled demos and games of the XGS ME (`.hex` and `.obj` files). The window
is drawn with SDL2.

[Try it in the browser](https://rainerblessing.github.io/xgsemu/)

## Status

Implemented:

- **CPU**: the SX52 instruction set with exact cycle counts, the real time
  clock/counter (RTCC) with its prescaler, the MODE register and the port
  control registers, and the carry input of ADD/SUB that a program selects with
  the CF fuse.
- **Video**: NTSC video as the program generates it (sync, colour burst, luminance
  and chroma), shown as a 560x525 picture. The colours follow the colour wheel of
  the hardware and are an approximation of a real TV.
- **Sound**: the three channels of the BU8763 in melody mode (sine or square wave,
  envelope, attenuation, master volume), played through SDL2 audio.
- **SRAM** (128 KB) and the **first joystick**.

Missing:

- Interrupts (RTCC overflow, `reti`, `retiw`), `sleep` and the watchdog
- Timers T1 and T2, the comparator and the wakeup/interrupt inputs of port B
- The DTMF/tone mode of the BU8763
- Keyboard and the second joystick

Known limits: the pitch of the sound is based on the nominal master clock of the
BU8763 (5.376 MHz). The XGS ME documentation also mentions 5.736 MHz, which would
make everything about a semitone higher. This is not settled.

## Hardware requirements

The emulator has to execute 80 million clock cycles per second (about 47 million
instructions per second) on **one CPU core**. More cores do not help.

Measured on an AMD Ryzen 7 9800X3D (one of the fastest single core CPUs), without
window and sound, for four of the example programs:

| Build | Speed compared to the real XGS ME |
|---|---|
| Release (`-DCMAKE_BUILD_TYPE=Release`) | 4.3 to 6.6 times faster |
| Debug (the default of the CMake file) | only 1.2 to 2.0 times faster |

So:

- **Use a Release build.** A Debug build is too slow on most PCs to run at 100%.
- With a Release build, a PC with about a third of the single core speed of that
  CPU should still reach 100% (an estimate, not measured). Slow systems such as a
  Raspberry Pi are borderline and untested.
- Memory is no concern (a few MB). A sound device is optional, without it the
  emulator runs silently.
- The window needs an SDL2 renderer with acceleration (OpenGL, Direct3D, Metal,
  ...). Without a GPU, starting with the environment variable
  `SDL_RENDER_DRIVER=software` selects the software renderer.
- Tested only on Linux.

## Building from Source

### Prerequisites

- CMake 3.10 or later
- A C++ compiler with C++11 support
- SDL2
- Git and a network connection when the tests are built (CMake downloads
  GoogleTest), or switch the tests off with `-DBUILD_TESTS=OFF`

### Build Instructions

0. The CPU is the git submodule [sxcpu](https://github.com/RainerBlessing/sxcpu).
   Clone with `git clone --recurse-submodules`, or run
   `git submodule update --init` in an existing clone.

1. Create a build directory:

```bash
mkdir build
cd build
```

2. Configure the project. Without `CMAKE_BUILD_TYPE` CMake builds the slow Debug
   version, so ask for Release:

```bash
cmake -DCMAKE_BUILD_TYPE=Release ..
```

3. Build:

```bash
cmake --build .
```

4. The executable is `xgsemu` in the build directory.

### Browser version (WebAssembly)

Needs the [Emscripten SDK](https://emscripten.org). With it activated
(`source emsdk_env.sh`):

```bash
./build-web.sh
python3 -m http.server -d build-web   # then open http://localhost:8000
```

The examples are bundled into the page; other `.hex`/`.obj` files can be loaded
with the file button. Live version: <https://rainerblessing.github.io/xgsemu/>

| Key | Action |
| --- | --- |
| Cursor keys | Joystick: up, down, left, right |
| Space or Ctrl | Fire button |
| F5 | Reset the running program |
| M | Mute / unmute the sound (also the *Sound* button) |

Click the picture once so it receives the keys and the browser allows sound.

### Tests

The tests are built together with the emulator and run in well under a second:

```bash
./unit_tests
```

### Additional Build Options

To clean the build directory:

```bash
cmake --build . --target clean
```

For a complete cleanup, remove the build directory:

```bash
rm -rf build
```

To format the sources with clang-format (if it is installed):

```bash
cmake --build . --target format
```

If you have Git installed, you can create distribution archives in the build
directory:

```bash
# Create a ZIP archive from the main branch
cmake --build . --target git-archive

# Create a ZIP archive with version information
cmake --build . --target git-archive-tagged
```

## Running the Emulator

```bash
./xgsemu                        # starts without a program
./xgsemu examples/rem_pac_01.hex
```

The `examples` directory contains compiled demos from the XGS ME disc (a game, 3D
and plane effects, plasma, starfields and more). Rem-Pac starts with the fire
button.

There is no menu and no file chooser. Programs are loaded with the file name on
the command line or with `Ctrl+L`, which loads a `.hex` or `.obj` file (the first
one the file system lists) from the directory that was used last (it is kept in `~/.config/xgsemu` on Linux and
macOS and in `%APPDATA%\XGSEmu` on Windows, and starts as the current directory).

## Controls

|---|---|

| Left or right Ctrl | Fire button |
| F5 | Reset |
| F11 | Full screen on/off |
| Ctrl+L | Load a `.hex`/`.obj` file from the last used directory |

## Assembler and disassembler

Two small command line tools are built next to the emulator (not in the browser
version):

```bash
./sxasm game.asm game.hex       # assemble
./sxdis game.hex                # list the programmed ROM words
./sxdis -n game.hex             # the same, without labels
./xgsemu game.hex
```

`sxdis` prints `address: opcode  instruction` for every word that is not empty
(`0xFFF`). It cannot tell code from data, so a table shows up as instructions.
The targets of `jmp` and `call` get a label (`L` and the address, e.g. `L237:`),
so `jmp 37` after a `page 1` reads `jmp L237`. The page is the one set by the
`page` instruction in front of the jump, otherwise the page the jump stands in.
A target that holds no code stays a number. With `-n` there are no labels.

The source has one instruction per line, in the notation `sxdis` writes. Numbers
are hexadecimal (`0x` is allowed), case and blanks do not matter and `;` starts a
comment:

```
counter equ 10              ; a name for register 0x10
        org 0
start:  mov w, #5
        mov counter, w
loop:   decsz counter
        jmp loop            ; a label instead of an address
        setb status.2
        jmp start
table:  dw 123, start       ; raw 12 bit words
```

| Line | Meaning |
|---|---|
| `name:` | A label, alone or in front of an instruction. `jmp` uses its low 9 bits, `call` its low 8 bits; a `call` to a label in the second half of a page is an error. |
| `org addr` | Continue at this address. The ROM has 4096 words, unused ones get `0xFFF`. |
| `name equ value` | A name for a number (register, literal), usable everywhere a number is, also before the definition. |
| `dw value, ...` | Raw 12 bit words. Values can be numbers, names or labels (a label keeps its full address). |
| `autopage on` / `autopage off` | Puts `page n` in front of every `jmp` and `call` to a label on another page, until switched off. Off at the start. |

The registers have names: `rtcc`, `pc`, `status`, `fsr` and `ra` to `re`. `w`, `m`,
`option` and `wdt` are reserved, names are case sensitive and can only be defined
once. A name wins over a number spelled the same, so do not call a label `a` or
`ff`.

A `jmp` reaches only the current page of 512 words and a `call` only its first 256
words, so the page has to be switched with `page n` first. Without `autopage` you
write it yourself. With `autopage on` the assembler inserts `page n` in front of
each `jmp` and `call` to a label on another page. It takes the page of the
address a piece of code stands at as the page it runs in, so:

- A function on another page has to end with `retp`, which restores the page of
  the caller.
- Code must not run from the end of one page into the next without a jump.
- An inserted `page` takes one cycle. Leave `autopage` off in code where the cycles
  count (the video lines) and write the pages by hand. A `page` you wrote
  right in front of a `jmp` is not doubled.
- Numbers as targets (`jmp 1ff`) are left alone.

Inserted words move the labels behind them, the assembler takes care of that. Errors
are reported as `game.asm: line 7: unknown name loopp`. ID and fuses of the hex
file stay unprogrammed.

The same code is in [sxcpu](https://github.com/RainerBlessing/sxcpu) as
`assemble()`, `assembleSource()` and `disassemble()`.
